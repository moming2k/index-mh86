Delegate + Verify Workflow

A reusable prompt block for fresh agents/environments with no skill installed.

For a completely fresh agent/environment with no skill available, here's a copy-pasteable instruction block that reproduces the exact workflow we used. 
For this task, use this workflow — you (the orchestrator) never implement code directly:

1. Track it: create a task list with these stages — spec, dispatch, verify, review, ship.
2. Isolate: enter a fresh git worktree (never edit the shared checkout).
3. Recon yourself: read the real current code for every file you'll touch — never
   paraphrase from memory.
4. Write a self-contained spec to a scratch file: exact file/line citations, before/after
   examples, explicit out-of-scope list, a "don't over-engineer" guardrail, exact
   verify commands (real venv/interpreter paths, not bare `python`/`pytest`), and an
   explicit "no git commit/push" instruction for the implementer.
5. Dispatch implementation to Codex CLI directly (not any read-only Codex skill):
   `codex exec -C <worktree> -s workspace-write --skip-git-repo-check -o <out>/last-message.txt --json < <prompt-file> > <out>/events.jsonl 2> <out>/stderr.log`
   run via Bash with run_in_background: true. Never trust the immediate tool return —
   wait for the real completion notification, then read last-message.txt.
6. Independently verify yourself — never trust Codex's self-report:
   - git diff --stat first: confirm only allowed files changed.
   - Read the full diff yourself.
   - Re-run the exact verify commands yourself, for real (Codex's own sandbox often
     can't reach the network or bind sockets — that's a dispatch environment limit,
     not proof the code is broken; re-check in your own environment).
   - If it's observable (CLI command, endpoint, extension), exercise it for real once.
   - If you find a real bug, dispatch a new, narrowly-scoped Codex fix — don't patch
     it yourself.
7. Dispatch a fresh, independently-scoped Agent for adversarial review — never reuse
   the implementer. Tell it explicitly: re-derive correctness from real code (the spec
   can be wrong), specific things to hunt for, and to fix anything real within its
   allowed files before reporting back.
8. Ship: commit with a message file (git commit -F), write a PR body to a file if
   there's a remote, push, open the PR. Do NOT merge without the user's explicit
   go-ahead — a prior "merge it" authorizes that PR, not future ones.

Never implement directly yourself. Codex and the review agent produce diffs; you do
recon, spec-writing, verification, and all git operations.
